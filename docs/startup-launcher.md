# Optional startup launcher

Arcify can offer **Open Arcify sidebar** when Chrome starts. With a ready paired Spotlight new-tab page, the command can be selected there; otherwise Arcify can show its small, ordinary launcher tab. Both require a real user action to open the sidebar.

## Enable or disable

In **Arcify Settings → Browser startup**, turn **Offer Arcify at browser startup** on or off. It is off by default and takes effect at the next browser startup. This keeps the existing `startupLauncherEnabled` setting and its saved value; nothing is enabled automatically. Existing settings, spaces, bookmarks, archives, tabs and bridge pairing are preserved. Turning it off does not close tabs Chrome has already restored; close an existing launcher tab normally if you no longer want it in the restored session.

## Paired Spotlight command

Spotlight advertises `startupSuggestion` and Arcify advertises `openSidebar` as optional `hello` capabilities. An older companion without the capability retains the previous launcher behavior. At startup, only the unchanged, focused, ordinary-window candidate within the existing short foreground deadline is eligible. Arcify offers to its current paired Spotlight new-tab page; it does not create a Spotlight tab or activate a restored one. Spotlight accepts only a ready, visible, empty and untouched page. Chrome may report a new-tab override as `chrome://newtab/`; the receiving extension page verifies its own tab identity rather than treating that alias as proof of ownership.

Arcify persists its once-per-session claim before sending the offer. Acceptance, user-interaction/ineligible refusal, malformed reply, timeout or an interrupted worker consumes the request, preventing a competing fallback. A confirmed `not-ready` refusal can create only a background launcher. No prompt is applied later after a refusal. If the user types, selects another result, or switches away, startup must not change that choice.

An eligible active Spotlight page is offered the command even if an inactive legacy launcher was restored elsewhere. Restored/manual helpers are left untouched. When no offer is available or Spotlight is not ready, an existing helper is reused without selecting it or creating another tab.

When Spotlight has keyboard focus, a real Enter or click sends a dedicated `{ type: 'arcify-sidebar', version: 1, requestId }` message directly to Arcify. Arcify uses one callback-style storage read to authenticate the current pairing, then immediately calls its own `sidePanel.open({ tabId: sender.tab.id })` in that callback. The command never runs through workspace queues, snapshots, timers, or an awaited authorization chain. It accepts no request-supplied target. The response is correlated with the same type/version/request ID, `role: 'arcify'`, and `ok` plus a structured error on failure.

The dedicated endpoint permits only the paired top-frame, active, non-incognito source tab: either Spotlight's exact extension new-tab page/origin, or its content script on an HTTP(S) page whose sender URL and origin match the browser-supplied source tab. Outbound pending navigation, mismatched origins/documents, subframes, inactive document lifecycles, file/restricted pages and missing tab context are rejected. This does not broaden the general workspace bridge's `trustedSender`, add a website listener, grant workspace access to content scripts, or add permissions. Browser enforcement still rejects calls without a genuine user gesture.

Chromium preserves message gestures in [MV3 worker delivery](https://raw.githubusercontent.com/chromium/chromium/main/extensions/renderer/api/messaging/native_renderer_messaging_service.cc) and carries an original worker interaction through [one API callback](https://raw.githubusercontent.com/chromium/chromium/main/extensions/renderer/extension_interaction_provider.cc). This source-backed route still needs real Helium acceptance. Chrome's [new-tab focus guidance](https://developer.chrome.com/docs/extensions/develop/ui/override-chrome-pages#best-practices) gives the address bar initial focus; a highlighted command does not guarantee that the first Enter reaches Spotlight. A visible command can always be clicked. If opening is rejected, retry with a fresh gesture or use Arcify's launcher/toolbar action; navigating to the launcher cannot reuse an old gesture automatically.

The launcher never opens the sidebar automatically. Chrome requires a real user action. Click the button, or focus it with Tab and press Enter/Space. Its native button calls `chrome.sidePanel.open({ tabId })` immediately from the trusted click handler. The page resolves its own tab ID before enabling the button; Chrome finds that tab's current window even after a tab move. There is no message, asynchronous lookup, synthetic click or timer ahead of the call. Rejected calls show a retry/toolbar-icon fallback. The page stays open after success, so the user chooses when to close it.

`sidePanel.open()` requires Chrome 116 or a compatible browser. On unsupported browsers the page explains the toolbar-icon fallback. See [Chrome's Side Panel API](https://developer.chrome.com/docs/extensions/reference/api/sidePanel#method-open).

## Startup and restore behavior

- At most one startup prompt or successfully created launcher per browser session, only after `runtime.onStartup`. Installation, an extension reload, worker suspension/resumption, subsequent windows and changing the setting do not independently create startup prompts.
- A short 750 ms quiet period allows startup tabs to restore. Background restore events do not continually reset this timer. A stored pending request and a separate one-shot alarm cover service-worker interruption; existing auto-archive startup/alarm hooks continue unchanged.
- Only ordinary, non-incognito browser windows with existing tabs qualify. Arcify never creates a browser window for the launcher. If none exist yet, it waits for one.
- The first focused normal window can become the startup candidate even if it appears after the startup event. Its new tab may be foreground during the first three seconds, after a short stable period, provided the selected tab and URL still match. Changing the candidate tab, navigating it elsewhere, or focusing another window suppresses foreground. Ordinary page loading, background-tab restoration, and repeated activation/focus for the same candidate do not count as user activity. Later readiness or an interrupted worker uses a background tab. No existing window is focused, and no browsing tab is navigated or removed.
- Existing or pending launcher tabs are reused without activation. If a restored launcher arrives after a new one was created, only the redundant tab created by this startup can be removed, and only while it is still the launcher with no outbound navigation pending and another tab remains in that window. A window is never closed just to remove a redundant helper. Manually opened/restored tabs are never deleted. Closing the launcher does not trigger another launch in the same session.
- A definite tab-create API rejection restores the pending request. Each retry rescans windows and existing launchers first; timer retries back off and stop after the initial 30-second recovery window. Later window/tab readiness events can resume a still-pending request, but can never take foreground after the three-second startup deadline. An interrupted, unresolved create retains its claim rather than being blindly replayed. Alarm cleanup is best-effort and cannot prevent creating the tab.

Chrome does not expose a single definitive “session restore finished” event or all user interactions inside webpages to an extension with these permissions. The bounded candidate check avoids delayed focus stealing while separating initial restoration from actual candidate changes. An already-restored inactive launcher remains inactive: it is reused without creating or selecting another tab, so this setting does not guarantee a visible prompt for that restored-tab case. Extremely late restore is handled by the duplicate check, rather than waiting indefinitely before showing the launcher.

## Isolation

There are no manifest permission additions and no new-tab override. Spotlight retains its existing new-tab behavior. The launcher is excluded from Arcify space membership, space snapshots, native-group sync, sidebar rows/native pinned favicons, archives, background recent/search-tab results and Spotlight bridge tab snapshots. The exclusion checks Arcify's exact helper URL, including pending restores; similarly named websites and other extensions are unaffected. Navigating the helper tab to an ordinary website makes it a normal browsing tab again.

The page uses only local assets and a small standalone script and stylesheet. It contains no dashboard, remote requests, workspace management UI or automatic side-panel activation.

## Verification

Automated unit/API/DOM regressions cover disabled defaults, saving/restoring the option without erasing other settings, capability negotiation, pairing revocation, strict source/envelope validation, callback-to-open ordering, accepted/declined/uncertain startup outcomes, cold-worker claims, startup foreground/background decisions, late windows, session persistence, existing/pending/late restored launcher reuse, repeated events, closing/no reopening, outbound navigation safety, API errors, synthetic-click rejection, synchronous button-to-API ordering, tab-ID targeting, accessibility markup and classification/archive exclusion. Production and development builds include the launcher page. Mocked trusted events and callback scopes do not demonstrate real browser user activation.

The earlier cold-start ordering and failure fixes reproduce in API fixtures. Later Helium diagnostics showed the current files on disk but no startup session marker; the launcher appeared after an explicit extension reload. Rebuilt unpacked worker files require an extension reload, so disk source and a fresh browser process alone do not identify the executing worker. After rebuilding, reload both extension cards before a full browser restart for startup acceptance.

Real-browser acceptance must use a sandboxed, permitted Chrome environment. Cloud browser execution was policy-blocked in this development environment; no sandbox/security bypass was attempted and no real-click side-panel success is claimed.

### Manual acceptance in an allowed browser

1. With the setting off, restart Chrome: no new launcher. With it on, restart using both a blank startup and **Continue where you left off**: at most one automatic launcher, existing tabs preserved, Spotlight still owns Ctrl/Cmd+T.
2. Restore a session containing a launcher; verify it is reused without an unexpected tab/window switch. Close it and open more windows: no repeated launch until the next full browser startup.
3. Test an initially focused normal window, a popup, multiple windows, a delayed normal window and an incognito window. Start browsing promptly: delayed launch should remain in the background.
4. On the launcher, click the button and separately use Tab then Enter/Space. Verify the real sidebar opens in that window. Drag the launcher to another normal window and repeat. Close/reopen the sidebar and retry; success must not depend on a simulated activation.
5. Check the launcher is absent from spaces, native-group membership, archive, recent/search results, pinned favicons and Spotlight bridge results. Navigate that tab to a website and verify ordinary classification resumes.
6. Disable the setting, close the helper, restart and verify no new helper. Verify previously saved settings, spaces, pins and archives remain unchanged.
7. With both companions reloaded and paired, restart onto Spotlight. Verify the command is selected only in an empty, untouched, visible startup page; record whether the omnibox or Spotlight actually owns keyboard focus. Test a physical Enter and click, both with a warm Arcify worker and after it stops. Verify the native Arcify panel is visibly mounted in the source window, not just a successful API response. Type or select another result before readiness and verify no late selection or foreground fallback. Repeat with an inactive restored launcher: the Spotlight offer must leave that helper untouched and must not create another.
8. Open Spotlight on an ordinary HTTP(S) webpage and invoke the command. Verify the same source window, fresh pairing revocation errors, unsupported/restricted source handling, and no side panel on startup alone or on an untrusted synthetic event. A fallback launcher requires a new real click/Enter after navigation.
